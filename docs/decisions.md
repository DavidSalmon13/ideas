# Decisions

Choices made where the docs didn't settle the question. Newest last.

- **2026-09-23 — Minimal API in the foundation step.** Phase 0's acceptance ("`docker compose up` starts API") needs something to run, so the repo step ships a FastAPI app with only `GET /health` (`opp.api.app`). Real routes come in their phases.
- **2026-09-23 — Compose binds to localhost.** `127.0.0.1:8000` only, per plan.md §18 (no auth in MVP, localhost bind by default).
- **2026-09-23 — Ruff skips Markdown.** Ruff would reformat the Python snippets inside `plan.md`; the design docs are excluded from linting/formatting.
- **2026-09-23 — Python pinned to 3.12.x** (`>=3.12,<3.13`) to match plan.md §2 and the Docker base image.
- **2026-09-23 — Alembic baseline is empty.** Revision `0001` creates no tables; plan.md §24 puts the domain tables in Phase 1, which will add them as `0002`. The baseline just proves `alembic upgrade head` runs.
- **2026-09-23 — Settings use the `OPP_` prefix.** e.g. `OPP_DATABASE_URL`, `OPP_LOG_LEVEL`. Only settings used today exist; provider keys, budgets and model routing are added in the steps that need them.
- **2026-09-23 — Default database is `./data/opp.db`.** The `data/` folder is git-ignored and mounted as the Docker volume, so backups are "copy that file" (plan.md §29). The container runs `alembic upgrade head` on start.
- **2026-09-23 — Logs redact secret-looking fields.** Any log field whose name contains key/secret/token/password is written as `***` (plan.md §18, §31).
- **2026-09-23 — "Offline" CI is enforced in the tests.** A `tests/conftest.py` fixture blocks every non-loopback network connection, so a test that forgets a fake or cassette fails instead of quietly calling a real API. Installing dependencies in CI still uses the network.
- **2026-09-23 — CI also smoke-tests Docker Compose.** A second job runs `docker compose up --build` and waits for `/health`, covering the Phase 0 acceptance check that can't run in the dev container.
- **2026-09-23 — `unknown` is a fourth claim type.** specs.md lists `fact | estimate | assumption` for claims but also requires economics values tagged `verified | estimated | assumed | unknown`, and intent.md treats "could not verify" as a first-class answer. `Claim.type` therefore allows `unknown`, and `Claim.value_status` maps the four types to the four tags.
- **2026-09-23 — `None` vs. `unknown` in an Opportunity.** A claim-typed field is `None` until the stage that fills it runs; a stage that looked and found nothing records an `unknown` claim. This keeps "not researched yet" separate from "could not determine".
- **2026-09-23 — Unsourced facts are allowed by the model.** The auto-demote rule belongs to the Evidence validator (next Phase 1 step), so `Claim` accepts a `fact` with no sources rather than rejecting it.
- **2026-09-23 — Claims point to sources by id.** `Claim.source_ids` holds Source ids (specs.md §8.1 "Source refs"); Sources are stored once and shared.
- **2026-09-23 — Ranges on claims.** `Claim` has optional `value_low`/`value_high` next to `value`, because specs.md §14 asks for "ranges over points when uncertain".
- **2026-09-23 — Rules enforced in the models.** Blank `confidence_reason` is rejected; dimension scores are 1-5 and unique; any override (hard gate or fatal flaw) requires a `kill` verdict; a stage allows at most one kickback; a report halted at a stage must be marked incomplete. `HALTED_*` runs are not terminal because they can be resumed.
- **2026-09-23 — Not modelled yet.** `Profile` (gates/weights) is config and comes with the profiles work; `stage_state` lives in the Stage/AgentRun records rather than on the Opportunity. The default profile id is `bootstrap`.
- **2026-09-23 — DB tables store aggregates as a JSON document plus projected columns.** Each row keeps the whole Pydantic object in a `data` JSON column (the source of truth on read) alongside a few real columns that exist only to power the plan.md §5 indexes/filters (status, verdict, dedup_hash, …). Repositories always derive the projected columns from the domain object on write, so the two can't drift. This keeps Pydantic the single boundary (plan.md §31) without hand-writing a column per field of the deeply nested Opportunity. The queryable `claims`/`sources`/`claim_sources` tables are a secondary evidence index; the Evidence Store step wires the extraction into them.
- **2026-09-23 — Foreign keys are `DEFERRABLE INITIALLY DEFERRED`.** The document store uses no ORM `relationship()`s, so SQLAlchemy can't order inserts by FK; a parent and its children written in one transaction would otherwise fail the mid-statement check. Deferring the check to COMMIT makes intra-transaction insert order irrelevant while still enforcing referential integrity (verified: a dangling ref is rejected at commit). Portable to Postgres, which supports the same clause.
- **2026-09-23 — Repositories don't commit; the caller owns the transaction.** Matches the incremental per-sub-task persistence in plan.md §5/§7. A generic `DocRepository` gives `add`/`upsert`/`get` for standalone aggregates; child records (Claim, Evaluation, Experiment) extend a read-only base and take their owner id on a custom `add`, since the domain objects are reused across owners and don't carry one.
- **2026-09-23 — Source `url_hash` is a plain digest for now.** `sources.url_hash` (the dedup key) is `sha256(url)`; URL canonicalisation (stripping tracking params, normalising host/scheme) and the semantic lead/opportunity dedup arrive with the Evidence Store step. The `dedup_index` table and a thin `DedupRepository` exist now (it's a table) but hold externally-computed hashes only.
- **2026-09-23 — Canonical URLs for source dedup.** `url_hash` now hashes a canonical URL: `http`→`https`, lowercase host without `www.`, default port/fragment/trailing slash dropped, `utm_*` and common click-ids (`gclid`, `fbclid`, …) removed, remaining query params sorted. It lives in `opp.evidence.dedup` (pure, no DB imports) so the DB layer can use it without an import cycle; `opp.db.repositories.url_hash` re-exports it.
- **2026-09-23 — "Semantic hash" = sorted content words, no embeddings.** A lead's fingerprint is `sha256(version | shape | customer words | pain words)` after lowercasing, dropping stopwords and folding simple plurals. Why-now and title are left out (same customer + pain + shape is the same opportunity). Looser rewordings are caught by a token-overlap similarity (both customer and pain ≥ 0.6, same shape) against the run's own leads; cross-run checks use the exact hash in `dedup_index`. Embeddings would add an API call and cost for little gain at MVP scale.
- **2026-09-23 — "Merged (strongest evidence wins)" = keep one, kill the other.** Near-duplicates aren't combined field by field; the lead with the higher evidence score (source credibility tiers + claim confidence; ties keep the earlier lead) survives and the other gets status `duplicate` plus a `Kill` with `failed_gate=duplicate`.
- **2026-09-23 — Save and index are separate.** `EvidenceStore.save_lead` validates and stores; `index_lead`/`index_opportunity` write to `dedup_index` only when the caller (triage, the operator's discard) decides the item's fate. An opportunity is indexed under its own fingerprint *and* its lead's, so discarding it also blocks that lead from coming back.
- **2026-09-23 — Validator rules beyond the obvious.** A source ref that doesn't resolve to a stored Source is dropped (a fact needs a *retrievable* source). A quantitative fact backed only by low-tier sources becomes an `estimate` (specs.md §7.2). Sources are independent when their publisher differs, or their host when there's no publisher. Conflicts are made two-way and conflicted claims are capped at `medium` (a cap rather than "one level lower", so the pass is idempotent; Synthesis may lower further). Every change is noted on the claim's `notes`.
- **2026-09-23 — Assumption load.** Share of a section's claims that are `assumption`, `unknown` or `low` confidence; every claim in a section counts as decision-critical until profiles define which ones feed gates/weights. A section is flagged above 0.5. Opportunity sections: problem, customer, market, competition, why_now, business_model, economics, small_team_feasibility.
- **2026-09-23 — Staleness is not checked yet.** specs.md §26.6 leaves the threshold open and Refresh is V1, so the validator doesn't flag stale claims for now.
- **2026-09-24 — Tavily is the default search adapter.** plan.md §2 lists Tavily/Brave/Exa; Tavily is first, returns content snippets (what snippet-first discovery needs) and has a flat per-call price. It's called over plain httpx (moved from dev to runtime deps) rather than a vendor SDK. Price per call is a setting (`OPP_SEARCH_COST_PER_CALL_USD`, default $0.008 for a basic search) because vendor pricing changes.
- **2026-09-24 — Search metering is a wrapper, not the provider's job.** Providers report `cost_usd`/`latency_ms` on each response; `MeteredSearch` (bound to a run/stage/agent) turns every call, including failures, into a `Trace` via an injected sink. The sink will be the trace repository once the runtime exists; keeping it a callable avoids giving the research layer a DB dependency.
- **2026-09-24 — Search failures raise `SearchError` after bounded retries.** Timeouts, connection errors, 429 and 5xx are retried (default 2 retries, exponential backoff from 1s, honouring a numeric `Retry-After` up to 30s); 4xx and malformed responses fail at once. Callers degrade to `unknown` (plan.md §17). Results with a non-http(s) URL or empty snippet are dropped because they can't back a claim; unparseable publish dates become `None`.
- **2026-09-24 — Search caching comes with the next step.** plan.md §17 caches search results and pages together in SQLite; that ships with the Fetcher/cache item rather than here.
- **2026-09-24 — A `FakeSearchProvider` lives in `src/`.** Agent tests in later phases need an offline provider, so it's importable from `opp.research.fake` rather than hidden in `tests/`.
- **2026-09-24 — Fetcher pins the vetted IP.** plan.md §18 says "DNS-resolve-then-check". To make that sound against DNS rebinding, the Fetcher resolves the host itself, requires *every* address to be globally routable (IPv4-mapped IPv6 unwrapped; CGNAT, link-local/metadata, multicast, reserved all refused), then connects to that IP with the original `Host` header and TLS `sni_hostname` (which Python's ssl also uses for certificate checks). Redirects are followed by hand (max 5) and each hop is re-checked. Keep-alive reuse is off so a TLS session verified for one hostname never carries another's request. Environment proxies are ignored (`trust_env=False`) because a proxy would do its own DNS. Tested with a mock transport only; the first live run should confirm https against a real site.
- **2026-09-24 — Fetcher limits.** Ports 80/443/8080/8443 only; no credentials in URLs; text content types only (HTML, XHTML, XML, plain text), so PDFs are out for now; bodies are streamed and capped at 2 MB (truncated, flagged `truncated`), and an oversize `Content-Length` is refused up front; 15s total timeout. All of these are settings except the port and type lists.
- **2026-09-24 — Extraction with trafilatura, pure and offline.** `extract()` runs trafilatura's main-content extraction with metadata (title, date, site name, author); plain text passes through. Extracted text is still untrusted and must only reach prompts inside DATA blocks (plan.md §15).
- **2026-09-24 — Static credibility rules; unknowns are low and flagged.** `classify()` uses domain and path rules (government suffixes → regulatory/high; known research firms → industry_report/high; major press → trade_press/medium; review sites, job boards → medium; forums, social, blog hosts → low; `/pricing` → pricing_page/high; docs/help → vendor/medium). Anything else is `other`/`low` with `confident=False`, ready for the LLM tie-break that specs.md §26.4 recommends once the LLM gateway exists. Low is the safe default because a low-tier source can't carry a quantitative fact alone.
- **2026-09-24 — Source fields.** A Source keeps the URL as given (after redirects), not the canonical form, since forcing https could break http-only sites; dedup uses the canonical hash. Excerpts are whitespace-collapsed and capped at 500 characters.
- **2026-09-24 — Cache: SQLite tables, own sessions, free hits.** `search_cache` (key = provider + normalised query + k + freshness) and `page_cache` (key = canonical-URL hash) hold JSON with an expiry; defaults are 7 days for searches and 30 days for pages (settings). The cache wrappers keep the provider/fetcher interfaces, commit in their own short sessions (the cache is shared across runs, outside any run's transaction), never cache failures, and return cached search responses with `cost_usd=0`, so reuse still shows up in traces as a free call. DB calls are synchronous inside async code; that's fine for one user on SQLite.
- **2026-09-24 — Anthropic SDK behind a neutral provider interface.** `opp.llm.types` defines `LLMProvider.complete(CompletionRequest) -> Completion` (text, stop reason, token usage); `AnthropicProvider` is the only adapter and the only module importing `anthropic`. The gateway owns tier routing, validation, re-asks, fallback and metering, so another provider only needs a new adapter.
- **2026-09-24 — Structured output: API-side schema, gateway-side validation.** The adapter sends `output_config.format` with `anthropic.transform_schema(OutputModel)` and uses `messages.create`, not `messages.parse`: `parse` validates inside the SDK and raises before token usage is visible, which would leave invalid attempts unmetered. The gateway validates with `model_validate_json` (so the model's own validators run too) and re-asks up to 2 times with the listed errors (plan.md §6), keeping the conversation append-only.
- **2026-09-24 — Default models and fallbacks.** Per plan.md §16: cheap = `claude-haiku-4-5`, medium = `claude-sonnet-5`, premium = `claude-sonnet-5`, premium with the Opus switch = `claude-opus-4-8`. Fallbacks (used only after the SDK's own 2 retries fail on 429/408/409/5xx/overload/network): cheap → `claude-sonnet-5`, medium and premium → `claude-sonnet-4-6`, Opus → `claude-sonnet-5`. All are settings (`OPP_LLM_*`). Refusals, bad requests and truncated output don't fall back: they aren't outages. A fallback restarts the conversation on the new model.
- **2026-09-24 — Prices live in code and gate routing.** `opp.llm.pricing` holds first-party list prices per model (cache writes 1.25x, reads 0.1x input). The gateway refuses to start if any routed model has no price, because an unpriced call would slip past the $20 meter. Cost is priced by the requested model ID. A simple pre-flight estimate (~4 chars/token, full `max_tokens` output) is there for the runtime's budget pre-checks.
- **2026-09-24 — No thinking/effort/temperature parameters yet.** Requests send only model, system, messages, `max_tokens` (default 16k, non-streaming) and the output format, so every model's defaults apply (Sonnet 5 thinks adaptively by default; Haiku 4.5 doesn't think). Thinking tokens are billed as output and are in the metered usage. Per-agent effort tuning waits for real cost calibration (Phase 8).
- **2026-09-24 — API key.** `OPP_ANTHROPIC_API_KEY` is optional; when it's empty the SDK's own resolution applies (`ANTHROPIC_API_KEY`, or an `ant auth login` profile). The key is a `SecretStr` and is never logged or put in error messages.
- **2026-09-24 — Cassettes record at the provider interfaces, not at HTTP.** plan.md §20 mentions respx for HTTP plus a recording wrapper for the LLM gateway. One mechanism covers all three instead: `CassetteLLMProvider`, `CassetteSearchProvider` and `CassetteFetcher` implement the same protocols as the real ones and store provider-neutral requests/responses as JSON. Cassettes therefore never contain API keys, auth headers or SDK wire details, keep working if an adapter changes, and replay with no real provider at all. The adapters' own HTTP handling stays covered by the mock-transport tests from earlier steps. The code lives in a new `opp.cassettes` package (plan.md §3 names `tests/cassettes/` only for the files).
- **2026-09-24 — Replay is strict.** A request with no recording raises `CassetteMissError` instead of calling out, so a test can't silently go live. The LLM key includes the output model's name and a hash of its JSON schema, so changing an agent's contract forces a re-record. Identical requests replay in recorded order, then keep returning the last recording. Errors (search, fetch/blocked, LLM outage) are recorded and replayed too, so degrade paths can be tested end to end. Modes are `record` (fresh file), `replay` and `once` (fill in missing).
- **2026-09-24 — No cassette settings yet.** Nothing in the app records or replays by config today; the CLI (Phase 3) is the first place that will wire a cassette in, so the switch (e.g. `OPP_CASSETTE_MODE`) is left to that step.
- **2026-09-24 — Agents are sub-task machines; the runtime owns everything durable.** `Agent` has `plan()` (sub-task ids) and `run_subtask()` returning a `SubTaskResult`; the runtime commits each result in one transaction (sources deduped and claim references remapped to the stored ids, claims/leads validated through the Evidence Store, ledger move, summary, agent and run cost). This realises plan.md §6's `run(ctx) -> AgentResult` as a loop the runtime drives, so resume and at-most-one-lost-sub-task hold for every agent without each one re-implementing them.
- **2026-09-24 — Compaction is deterministic by default.** Working memory = persisted summary + recent notes; agents must build prompts from it. Before every LLM call and every sub-task, memory over ~8k estimated tokens is folded into a new summary (bounded at 6k chars, most recent work kept; older detail already lives in committed claims) and persisted. No model call is spent (intent.md §21.2: "a memory operation"); an agent can override `compact()` if it needs a smarter summary.
- **2026-09-24 — Budget guard pre-checks with upper-bound estimates.** Each call is checked against the agent's `ResearchBudget` (dollar cap + LLM/search/fetch call caps) and the shared run budget before it's made; LLM estimates use the priciest model on the route and the full `max_tokens` output, searches use the configured per-call price. Re-asks inside one gateway call aren't pre-checked separately, so a call can overshoot its estimate by its re-asks; the run ceiling is still enforced at every next call. Actual cost is charged from what the gateway/providers report.
- **2026-09-24 — New `halted_budget` agent-run status.** A budget stop leaves the sub-task pending and `ended_at` empty so a top-up resumes it; it isn't a failure. Per-agent call counts aren't persisted, so a resumed agent gets its call caps afresh (its dollar spend is restored from the agent run).
- **2026-09-24 — Failure handling in the runtime.** LLM, search, fetch and oversized-prompt errors mark just that sub-task failed (recorded in a new `WorkLedger.failed` list and in memory) and the agent ends `degraded`. Any other exception ends the agent run `failed` with the error recorded; the runtime never raises into the orchestrator. Using an undeclared tool counts as a bug. Traces are written the moment a call finishes (`DbTraceSink`, own session), so a crash mid-sub-task never hides spend.
- **2026-09-24 — Discovery queries come from recipe templates, not the model.** Each signal source's recipe (`prompts/discovery/v1/recipes.json`) holds six query templates filled with the run's scope (target customer, industry, geography); one sub-task = one query. Templates are free, deterministic and resumable, and keep "parametric brainstorming" out of discovery entirely; an open-ended run simply uses the templates without a subject.
- **2026-09-24 — Discovery is snippet-only and cites by snippet number.** The cheap-tier extraction sees only the numbered search snippets (inside the untrusted DATA block) and must cite snippet numbers per claim. Cited claims become `fact` claims tied to those sources; uncited ones become `assumption`; an empty why-now becomes an `unknown` claim. A lead none of whose three claims cites a real snippet is dropped, and only snippets a kept lead cited are stored as sources. No page fetches at this stage (plan.md §17 "snippet-first"; fetching is spent later on earned depth).
- **2026-09-24 — Lead target is split evenly across signal sources** (`ceil(discovery_n / sources)`, default 30 → 6 each), and each agent stops once it has committed its share. The count survives resumes via a new `AgentRun.output_counts` the runtime maintains. Default discovery research budget per agent: $0.75, 8 searches, 10 LLM calls, 0 fetches (settings), matching specs.md §21.2's $3–4 for discovery overall.
- **2026-09-24 — Dedup and generic-idea checks are left to triage.** Discovery doesn't consult the dedup index or the generic blocklist; triage (Phase 4) owns both, as specs.md §5.2 assigns them.
- **2026-09-24 — Discovery-only runs end `completed_partial`.** Until the orchestrator exists, `opp discover` runs just the discovery stage; the run ends `completed_partial`, or `halted_budget` / `halted_error` when agents ran out of budget / all failed.
- **2026-09-24 — CLI is plain argparse, installed as `opp`.** Subcommands `discover` and `leads`. It never creates tables itself (it tells you to run `alembic upgrade head`). `--cassette` replays offline by default; recording modes bypass the search cache so every call lands in the cassette. The command's core (`opp.cli.discover.run_discovery`) takes injected services, so tests and cassettes drive the same code.
- **2026-09-24 — Prompt templates use `$placeholders`.** `string.Template` rather than `str.format`, so JSON examples in prompts need no brace escaping; prompts live as package data under `opp/prompts/<agent>/<version>/`.
- **2026-09-27 — "No lead without a source" is enforced in the Evidence Store, not only by Discovery.** `EvidenceStore.save_lead` raises `UnsourcedLeadError` (writing nothing) when, after validation, none of the lead's claims cites a *stored* source. The runtime drops such a lead, notes it in the agent's memory, counts it in `AgentResult.leads_rejected`, and still commits the rest of the sub-task; refused leads don't count toward the lead target. Every future agent that emits leads gets the guarantee for free.
- **2026-09-27 — `opp resume RUN_ID` for discovery-only runs.** Until the orchestrator's recovery scan (Phase 4) exists, resume is an explicit CLI command. It accepts any non-terminal run whose current stage is discovery (interrupted `discovering`, `halted_budget`, `halted_error`), leaves finished agent runs alone and reruns the others through the runtime, which continues each from its ledger. Run spend on resume is `max(run.cost_to_date, sum of the run's traces)`, because traces are written per call and so include the sub-task that was lost in the interruption. `--budget` raises the run ceiling (must exceed what's spent); it doesn't lift an agent's own dollar cap, so an agent that hit its own research budget stays halted.
- **2026-09-27 — The kill test is a real SIGKILL.** Besides an in-process interruption, `tests/test_resume.py` runs discovery in a subprocess that SIGKILLs itself mid-run, then resumes it and checks only the owed work is redone and every lead is sourced.
- **2026-09-27 — Orchestrator shape.** `opp.orchestration.state_machine` holds the pure transition rules; `Orchestrator` (`orchestrator.py`) creates runs, advances them through `StageHandler`s (`stages.py`) and is the only code that changes a run's status. Every transition is checked against the rules and appended, with its reason, to a new `ResearchRun.transitions` list (kept in the run's JSON document, so no migration) — this is the "run diagnostics" of plan.md §19. Allowed side edges: any working state → cancelled / halted_budget / halted_error / completed_partial; kickback only from a post-research state to the one before it; a halted run only back to the state it halted in (resume) or to cancelled / completed_partial. `AWAITING_CHECKPOINT` can't halt (nothing is spent while waiting); autonomous runs skip it.
- **2026-09-27 — The funnel ends where the handlers end.** Stages without a handler yet (everything after discovery for now) aren't faked: the run moves into that stage's state and then ends `completed_partial` with the reason "the X stage is not available yet". As later phases add handlers to `default_handlers`, runs go further with no orchestrator change.
- **2026-09-27 — Stage rows and resume.** Re-entering a stage reuses its latest attempt unless that attempt completed (only a kickback re-enters a completed stage, and that makes attempt n+1). Halted and cancelled stages stay `running` with no end time; failed ones are `failed` but are still re-entered by a resume. Handlers must be resumable: the discovery stage reuses the stage's existing agent runs, which continue from their ledgers.
- **2026-09-27 — Signal sources are part of `DiscoveryScope`.** `DiscoveryScope.signal_sources` (default: all five) replaces the CLI-only `--signal` list, so a resumed or recovered run knows what to mine (plan.md §30: everything a run's behaviour depends on lives in RunConfig).
- **2026-09-27 — Recovery scan = `Orchestrator.recover()`, exposed as `opp recover`.** It continues runs in a working state (created or any funnel stage except the checkpoint) whose `updated_at` is older than `OPP_RECOVERY_STALE_AFTER_MINUTES` (default 15). Runs updated more recently may still be running in another process — there's no lock table for one user — so they're skipped unless `--all` is given. Halted runs and runs at the checkpoint wait for the operator and are never auto-resumed. The API has no run routes yet, so it doesn't call the scan on startup; that wiring comes with the run endpoints (Phase 7).
- **2026-09-27 — Cancellation is in-process.** `Orchestrator.cancel(run_id)` sets a flag checked between sub-tasks (the agents' `should_stop`) and between stages; a run that isn't in flight (halted, or at the checkpoint) is cancelled at once. Cross-process cancel (e.g. from the API while a CLI run is going) needs a persisted flag and comes with the API.
- **2026-09-27 — `opp discover`/`resume` go through the orchestrator.** The discovery-only helpers in `opp.cli.discover` are gone; that module now only formats a run's leads and per-agent summary (read back from the DB, so resumed runs show totals).
- **2026-09-27 — Profiles are code-level config records.** `opp.config.profiles` holds `bootstrap` (default; $2,000 / 120 days) and `micro` ($1,000 / 30 days) with relative dimension weights following intent.md §13.2's maximise / heavily-weight / de-prioritise lists (e.g. Bootstrap: time-to-revenue 3, margin/automation/capital/small-team 2.5, market/moat/scalability 0.5, rest 1). Weights are normalised; `RunConfig.weight_overrides` replace a profile weight before normalising, and the weights are cited as `bootstrap+overrides` when nudged. Adding a profile is adding a record. Gates are defined now but enforced by the Judge (Phase 6), since triage has no capital or time-to-revenue evidence yet.
- **2026-09-27 — Triage = deterministic dedup + rules + one cheap judgment per batch.** The stage first dedups the run's new leads (in-run near-duplicates merged, strongest evidence wins; anything matching the cross-run index is a duplicate, whether that entry was kept, killed or discarded — plan.md §22 "never re-research known items"). Then `TriageAgent` screens batches of 8: the three hard gates are checked *mechanically* first (each claim must be a sourced `fact`/`estimate`; a customer made only of generic words like "small businesses"/"developers" fails; a why-now matching vague-trend patterns like "AI is getting better" fails), then a cheap-tier call judges what rules can't (narrow customer, documented pain, specific why-now, why-unsolved, wedge, 1-5 specificity and small-team fit). The model can only *fail* a lead the rules passed; rule-killed leads never reach it. If the model is unavailable or skips a lead, the rules decide alone and the lead gets specificity/fit 1 so it ranks last. Decided leads go into the dedup index (kept → active, killed → killed).
- **2026-09-27 — Generic blocklist and its higher bar.** Patterns ("AI chatbot/assistant/copilot for X", "Uber/Airbnb for X", "productivity app", "app for small businesses", "all-in-one platform", "social network for X") are matched on title, wedge, customer and pain. specs.md §26.5 recommends (a) for the "higher bar": a flagged lead survives only if its pain claim rests on ≥2 independent (different publisher/host) high-credibility sources; otherwise it's killed with the new `FailedGate.GENERIC_PATTERN`. With snippet-only discovery this kills nearly all generic leads, which is the intent.
- **2026-09-27 — Cheap scores and ranking.** `source_strength` = 1 + the rounded-half-up sum of the lead's distinct sources' tiers (high 2, medium 1, low 0.5), capped at 5; specificity and small-team fit come from the model. `rank_score` = the mean of the three, +0.25 each for a specific wedge and a concrete why-unsolved (intent.md §16's "scored but not hard-kill" tests). Stored on `Lead.triage` (a `TriageAssessment` in the lead's JSON, so no migration).
- **2026-09-27 — Shallow validation: one search + one scoring call per candidate, no fetches.** The top `lead_targets.shortlist_n` (default 5) kept leads by `rank_score` each get one corroborating snippet search (customer + pain) and one medium-tier call scoring all 16 dimensions. The fetch budget specs.md §5.3 allows is left at zero for now: snippets plus the lead's quoted evidence already show what the rough score needs, and the Fetcher isn't wired into stages yet. Scores are held to their basis: `insufficient` ≤ 2, `inferred` ≤ 3, `sourced` needs a real citation (else it's treated as inferred); an unscored dimension is 1/insufficient. The model may add up to four findings, each a `fact` claim that must cite a snippet; uncited ones are dropped. A failed search degrades to scoring on the lead's own evidence.
- **2026-09-27 — Shortlist = Opportunities with a `ShallowScore`.** Each scored lead becomes an `Opportunity` (status `new`) seeded with the lead's customer / pain / why-now claims and wedge, plus `shallow` (per-dimension provisional scores, weighted composite, weights ref, rank) and `screening_claims` (the findings; included in `Opportunity.claims()` so validation, traceability and assumption load cover them). The `opportunities.composite` column shows the shallow composite until a Judge evaluation replaces it. Ranks are assigned once all candidates are scored (ties: earlier first). Rank 1 is the checkpoint's default pick; the rest are the promotable shortlist. Selection itself belongs to the checkpoint step.
- **2026-09-27 — Nothing surviving ends the run.** A new stage result `no_candidates` (no lead survived triage, or none could be scored) moves the run to `completed_partial` with that reason, rather than halting: it's an honest outcome, not an error (specs.md §3.4, plan.md §33 "too few results").
- **2026-09-27 — Agents can emit kills and opportunities.** `SubTaskResult` gained `kills` and `opportunities`; the runtime commits them in the same per-sub-task transaction (opportunities through `EvidenceStore.save_opportunity`, with source ids remapped like leads' claims; kills via the new `EvidenceStore.record_kill`).
- **2026-09-27 — A run at the checkpoint can't be "resumed".** `opp resume` refuses a run in `awaiting_checkpoint`; it needs a checkpoint decision (next step), not a resume.
- **2026-09-28 — The checkpoint decision lives on the run.** `ResearchRun.checkpoint` (a `CheckpointDecision` in the run's JSON, no migration) records `approve` (the rank-1 candidate), `pick` (a runner-up), `veto` (the whole shortlist) or `auto` (autonomous mode's rank-1), with the operator's one-line reason; re-picks and vetoes must give one (specs.md §2.7), stored for preference learning later. Picking the rank-1 candidate counts as an approval. A veto ends the run `completed_partial`; the shortlist stays as it is (still promotable in V1), nothing is discarded. The CLI is flag-driven, not interactive: `opp checkpoint RUN` shows the shortlist, `--approve` / `--pick ID --reason` / `--veto --reason` decide and continue the run. No `checkpoint` stage row is written; the decision and its transition are the record.
- **2026-09-28 — Stage minimums drive the pre-checks and the pre-flight.** Each stage has a minimum it must have left in the run budget before it starts: the lower ends of specs.md §21.2 (discovery 3, triage 0.5, shallow 3, deep research 5, synthesis 1, strategy 1, red team 1, judge 1 → $15.50, leaving ~$4.50 reserve under $20). Configurable as `OPP_STAGE_MINIMUMS_USD` (JSON, partial overrides). A run whose ceiling is below the sum is refused at creation (plan.md §22 pre-flight). Before each stage the orchestrator checks the remaining budget against that stage's minimum, less what an unfinished attempt of it already spent (so a resumed stage asks only for the rest); a shortfall halts the run `halted_budget` *before* the stage starts, with the amounts in the reason. Stages with no handler yet end the run as before; they aren't pre-checked.
- **2026-09-28 — Every early stop writes an incomplete report.** Any move to `halted_budget`, `halted_error`, `cancelled` or `completed_partial` stores a `Report` (`incomplete=True`, `halted_at_stage`) built by `opp.reporting.partial`: headline "INCOMPLETE — halted at stage X", no verdict (capped at promising-but-unproven; the Judge never ran), the best candidate so far (the checkpoint's pick, else the rank-1 shortlist item, none after a veto) with its claims and source URLs and its assumption load, the shortlist, funnel counts, the research axes never examined, cost by stage, and the next command (with a suggested `--budget` when the remaining ceiling can't cover what's left). A run that halts twice gets two reports; `opp report` shows the latest. The full report builder (Phase 6) replaces this for completed runs.
- **2026-09-28 — Specialists file loose claims; synthesis reconciles them.** The four deep-research specialists (customer, competition, market, feasibility) run in parallel on the one selected opportunity, each filing its axis claims *loose* — keyed by the opportunity via `SubTaskResult.opportunity_id`, stored through `save_claims` (which doesn't prune) rather than into the opportunity document. This is what makes the parallel runs safe: if each wrote the opportunity document, `save_opportunity`'s claim-prune would delete the others' claims (a lost update). Folding those loose claims into the structured Opportunity sections (`Customer`, `Market`, `Competition[]`, …) is deferred to the "full Opportunity assembly" step; for now the claims are queryable by `ClaimRepository.list_for_opportunity` and stage `deep_research`.
- **2026-09-28 — Specialists are snippet-first, like shallow validation.** Each specialist axis has a few research questions (`prompts/deep_research/v1`), one sub-task each: a snippet search shaped by the opportunity, then one medium-tier extraction over the snippets. Cited findings become `fact`/`estimate` claims; the model's uncited inferences are kept as `assumption` claims (never dressed up as facts); a question the search can't answer records an `unknown` claim, so "looked, found nothing" stays first-class. Page fetches (the fetch budget specs.md §5.4 allows) stay at zero for now — the Fetcher still isn't wired into stages (same call as shallow validation); fetch-on-earned-depth waits for cost calibration. Per-specialist budget: $1.5, 4 searches, 6 LLM calls; four run under the shared run budget (settings).
- **2026-09-28 — Synthesis records contradictions on the claims and a picture on the opportunity.** `SynthesisAgent` (one medium-tier call) sees every deep-research claim numbered and tagged with its axis, and returns a consolidated summary plus the sets of claims that conflict. Conflicts are written to the claims' own `conflict_ids` (the Evidence validator already makes them symmetric and caps a conflicted claim at `medium`, so the Judge sees them); the summary, a human-readable `Contradiction` list and the axes covered are attached to the opportunity as `Opportunity.synthesis` (a new `ResearchSynthesis`, in the opportunity's JSON, no migration). Synthesis reconciles only `deep_research`-stage claims for now; the lead's seed claims are left as they are. *(Superseded 2026-09-28 by the assembly step below: synthesis now folds the loose claims into the opportunity document and saves through `save_opportunity`, so the interim `EvidenceStore.save_synthesis` / `SubTaskResult.synthesis` scaffolding was removed.)*
- **2026-09-28 — Deep research and synthesis end where the handlers do.** With the two new handlers registered, an autonomous run now flows past the checkpoint through deep research and synthesis and stops at the not-yet-built strategy stage (`completed_partial`, "the strategy stage is not available yet"). A specialist or synthesis stage that finds no selected opportunity ends `no_candidates` rather than crashing.
- **2026-09-28 — The budget meter is a trace roll-up.** `opp.observability.cost.cost_ledger` sums a run's traces by stage, agent and call kind (with call and failure counts); spent = max(run.cost_to_date, traced), as for resume. `opp cost RUN` prints it with the least the rest of the funnel still needs; the run summary shows the same "needs at least $X" line.
- **2026-09-28 — Full Opportunity assembly = per-axis claim lists on the opportunity.** Synthesis now folds the specialists' loose deep-research claims into a new `Opportunity.research` (`Research`: `customer`/`competition`/`market`/`feasibility` claim lists), matching intent.md §11.3's `customer[]/competition[]/market_economics[]/feasibility_timing[]` rather than the granular `Customer.buyer`/`Market.size`/… named fields (those stay seeded from the lead and are refined later by Strategy; mapping free-form findings to individual named sub-fields would need an extra LLM pass for little MVP gain). `Research` is a `ClaimGroup` included in `Opportunity.claims()`, and the four axes are added to the validator's `opportunity_sections`, so per-axis assumption load and traceability cover the research. Because the claims now live in the opportunity document, synthesis returns the assembled opportunity via `SubTaskResult.opportunities` (through `save_opportunity`, whose claim-prune keeps them since they're in the document), and the interim non-pruning `save_synthesis` path from the previous step was removed.
- **2026-09-28 — Unknowns become validation-backlog experiments.** Every `unknown` claim in the assembled research becomes an `Experiment` on `Opportunity.validation_backlog` (method `desk_research`, leverage `low`, `assumption_claim_id` pointing at the gap, sequential priority), so "looked, could not determine" turns into a concrete next test (intent.md §17, §20; specs.md Phase 5 accept "unknowns recorded + queued as experiments"). They're stored inline on the opportunity for now; the `experiments` index table is wired later.
- **2026-09-28 — Strategy is one premium call over the research, adding no sources.** `StrategyAgent` (single `build_plan` sub-task, premium tier, LLM only — no search) reasons over the opportunity's assembled research (per-axis claims + synthesis summary + seed customer/pain/why-now) and returns a full `StrategyPlan`: proposed business, MVP, business model + pricing, distribution/acquisition, scenario unit-economics, small-team feasibility and a validation backlog. specs.md §5.6 allows a small fetch budget; it's left at zero for now (like the other stages — the Fetcher isn't wired into stages yet), and the strategist works from the research already gathered. Every figure it produces is an `estimate` (pricing, margins, scenario outputs) or `assumption` (labeled inputs, small-team judgments), never a `fact` — it cites no new source, and the Evidence validator would demote an unsourced fact anyway. Strategy figures are therefore `low`-confidence and push the economics section's assumption-load high on purpose: the estimates *are* unvalidated (intent.md §17), and the Judge down-weights accordingly. Budget: $1.5, 3 LLM calls, 0 searches (settings default). The `strategy` stage runs after synthesis and, with red-team/judge not built yet, an autonomous run now flows through it and stops `completed_partial` at the not-yet-built red-team stage.
- **2026-09-28 — Canonical assumptions live on the base scenario; each maps to an experiment.** The strategist's labeled assumptions become one `Claim` each (type `assumption`), stored once on the `base` economics scenario so no claim id appears twice in `Opportunity.claims()` (conservative/upside carry only their own output figures; the shared load-bearing set links them). `Economics.load_bearing_assumption_ids` holds the 1–3 the outcome is most sensitive to; `Opportunity.assumption_ids` ranks all of them (load-bearing first, then lowest-confidence first). The validation backlog is the strategist's experiments plus a fallback interview experiment for any load-bearing assumption it left untested, so **every** load-bearing assumption maps to at least one experiment (specs.md §17 accept); items are ranked highest-leverage first and appended after whatever Synthesis already queued (its unknown→desk-research items keep their earlier priorities). Strategy doesn't raise kickbacks yet (the `building_plan → synthesizing` edge exists but is unused); a strategy-driven kickback can be added when the red-team surfaces a research gap.
- **2026-09-28 — Red-team and judge are premium, LLM-only, one call each.** `RedTeamAgent` (stage `red_team`) sees the whole opportunity — the plan plus every claim (`Opportunity.claims()`, numbered, with their source excerpts) — and returns ranked, evidence-graded attacks; `JudgeAgent` (stage `evaluation`) then scores the 16 dimensions after reading the attacks and issues the verdict. specs.md §5.7 allows the red-team a small verification-fetch budget and §5.8 gives the judge db-only; both are kept **LLM-only** for MVP (no search wired into stages yet, same as strategy/synthesis) — they reason over the research already gathered. Budgets: $1.5 / 3 LLM calls each (settings), inside specs.md §21.2's $2–3 for red-team + judge. With both registered, an autonomous run now flows the **whole funnel** to `completed` (Milestone M1's engine path; the completed-run report builder is the next step, so `completed` runs don't emit a `Report` yet).
- **2026-09-28 — A fatal flaw must be well-supported.** An `Attack` stores `source_ids`, not claim ids, so the red-team cites the claim numbers it rests on and those claims' sources are copied onto the attack. `is_fatal` is honoured only when the attack cites at least one claim (intent.md §16, §33: "a sufficiently severe, well-supported attack"; reduce false positives) — a Kill is never forced on pure speculation. `RedTeamAnalysis.fatal_flaw` is true iff any honoured attack is fatal. Attacks are stored ranked by severity (critical→low), fatal first.
- **2026-09-28 — Non-compensatory overrides are deterministic, in `evaluation/framework.py`.** The Judge's LLM proposes per-dimension scores + a verdict; the framework then applies the rules the score can't buy back (specs.md §17.4). Hard gates read the strategist's economics **estimates**: `capital_required` (USD) vs the effective capital gate, and `time_to_revenue` converted to days (day/week/month/year units understood; an unrecognised unit is **not** gated, to avoid a false Kill on an ambiguous figure) vs the effective time gate. Effective gate = the run's `hard_gates_override` if set, else the profile's. Any breached gate, plus a red-team `fatal_flaw`, becomes an `Override`; **any** override forces `verdict=kill` regardless of composite (the `Evaluation` model already enforces overrides→kill). Dimension scores are held to their evidence with the same caps as shallow validation (sourced ≤5, inferred ≤3, insufficient ≤2; a "sourced" score citing nothing real is treated as inferred). The composite is the profile-weighted mean, ranking only.
- **2026-09-28 — Evaluation lives on the opportunity document; the evaluations table isn't populated yet.** The Judge writes `Opportunity.evaluation` and the run saves it through `save_opportunity`, which projects the `opportunities.composite`/`verdict` columns from the evaluation (replacing the shallow composite). The secondary `evaluations` index table (`EvaluationRepository`) stays empty for now, like the `experiments` table — the opportunity JSON is the source of truth and the report builder reads it from there; wiring the index is deferred with the other secondary indexes.
- **2026-09-28 — The completed-run report is a pure projection, no model call.** `opp.reporting.final.build_final_report` builds the 1-page brief + full dossier for a `completed` run entirely from the persisted opportunity (claims, economics, red-team, evaluation) — no LLM, no cost. Every brief element is derived, not re-reasoned: the thesis is composed from the customer/why-now/value-prop claims in specs.md §18.1's "[customer] pays for [X] because [why]" shape; the economics snapshot reads the base/conservative scenario output claims and resolves the load-bearing assumption ids to their claims; the "cheapest next experiment" is the highest-leverage, lowest-cost validation-backlog item, preferring one that tests a load-bearing assumption; confidence is the overall assumption-load plus the evidence-quality/assumption-risk dimension scores. The orchestrator emits it on the transition to `completed` (mirroring `_emit_partial` for early stops), so a finished autonomous run stores exactly one `Report` (`incomplete=False`).
- **2026-09-28 — Source-traceability is a stored invariant, not a render-time join.** The dossier carries every claim with its `claim_id` and resolved source URLs, grouped by section (problem, customer, market, competition, research axes, economics scenarios + assumptions + metrics, small-team, red-team, validation backlog, the full evidence list, and a `sources` map id→{url,title,tier}); the evaluation section lists all 16 dimension scores with their supporting claim ids. The brief's claim-typed elements (why-now, load-bearing assumptions, kill-risk attacks) carry the same source URLs, all of which resolve in the dossier's `sources` map — the test asserts this (specs.md §8.3, §25.10). Shared serialisation helpers (`_claim`, `_funnel`, `_prompt_versions`, `BriefClaim`, `ShortlistEntry`) are reused from `reporting.partial`.
- **2026-09-28 — `opp report` renders the decision brief for completed runs.** `format_report` now renders the completed-run brief as Markdown via `reporting.final.render_report` (was: dumping the brief JSON), and still renders the incomplete-run brief via `render_brief`. A completed run without a judged opportunity (which shouldn't happen — you can't reach evaluation without a selection) falls back to a minimal honest report rather than crashing.
- **2026-09-28 — Kickback (≤1/stage) is a stage result the orchestrator arbitrates.** Synthesis may set a one-line `blocking_gap` on its `ResearchSynthesis` when a decision-critical axis was left essentially unresearched; the `SynthesisStage` turns that into a new `StageResult.KICKBACK` (the stage's own work still stands — the stage is closed `completed`). The orchestrator sends the run back one stage along the existing `state_machine.KICKBACK` edges (synthesizing → deep_research), re-runs it, then synthesis again. The **≤1 per stage** cap is enforced by counting the target stage's attempts: a kickback is the only thing that gives a completed stage a second attempt, so a second kickback into a stage that already has two attempts is refused and the run proceeds instead of looping. The re-entered attempt is marked `kickback_count=1` for the report. A kickback re-runs all specialists (a fresh, budget-pre-checked deep-research attempt), not just the gap axis — simpler, and the cap bounds the cost.
